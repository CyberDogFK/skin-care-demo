1. Architecture overview
------------------------

Part A (Stages 1–3):

  User action (click, form submit, route change)
        |
        v
  React component  --->  CartContext actions / router.navigate()
        |
        v
  UI updates, cart saved to localStorage

Part B (Stages 4–5) adds one layer, without changing Part A's structure:

  CartContext actions / router / pages  --->  src/analytics/track.ts
                                                      |
                                                      v
                                   window.dataLayer.push({ event, ecommerce })
                                                      |
                                                      v
                                  Google Tag Manager -> GA4 tags, Meta tags

Key decisions:

a) Routing: a tiny custom router (~40 lines, History API: pushState +
   popstate) instead of react-router. Keeps dependencies minimal and gives
   ONE place where every route change happens (useful later for page_view).
   Routes:
     /                 Home (hero, catalog, benefits)
     /product/:id      Product details
     /cart             Shopping cart
     /checkout         Checkout form
     /confirmation     Order confirmation
   The router must respect Vite's base path (import.meta.env.BASE_URL),
   because GitHub Pages serves the site from /<repo-name>/.

b) State: React Context + useReducer for the cart (CartProvider + useCart
   hook), persisted to localStorage. No Redux. Cart changes go through
   named action functions (addToCart, removeFromCart, ...), never raw
   dispatch from components — this is good structure on its own and is
   also where Stage 4 will hook in analytics.

c) React StrictMode stays ON.

d) Privacy by design from day one: the checkout form data is validated
   in the browser only, never sent anywhere and never stored. The stored
   Order contains only products, totals, transaction id and the delivery
   METHOD id.

e) Hosting: GitHub Pages, built and deployed by a GitHub Actions workflow
   (free, HTTPS). Details in Stage 3.

f) Light + dark theme, CSS-variable based:
   - All colors are design tokens on :root (light = default). The dark set
     overrides the same token names; components never hardcode colors, so
     they work in both themes with no per-component dark CSS (except a few
     image tweaks).
   - Default = follow the OS (prefers-color-scheme). A header toggle lets
     the user pick light / dark; the choice is saved in localStorage
     "glowcare_theme" ("light" | "dark"; absent = system).
   - The active theme is set as <html data-theme="light|dark"> by a tiny
     inline script in index.html BEFORE first paint, so there is no
     flash of the wrong theme on load / refresh.
   - `color-scheme: light dark` so native form controls, scrollbars and
     autofill match the theme.

g) Git from the very first task, through all stages (see section 4).
   Deployment to GitHub Pages is NOT part of this — it stays in Stage 3.

Decisions deferred to Part B (Stage 4): page_view strategy, GTM ID
configuration via VITE_GTM_ID, dataLayer utility, data-gtm attributes.

4. Git workflow (applies to ALL stages)
--------------------------------------
Repository: git@github.com:CyberDogFK/skin-care-demo.git (already set up).

!!! RULE FOR THE AI ASSISTANT (Claude) — HIGHEST PRIORITY !!!
  NO COMMIT IS DONE BY THE AI WITHOUT THE USER'S EXPLICIT COMMAND.
  The same applies to `git push`, `git tag` and any other command that
  changes git history or the remote (amend, reset, rebase, revert,
  force-push).
  - The AI only edits files. When a piece of work is ready, it STOPS,
    reports what changed, proposes a commit message, and waits.
  - A command for one commit is not permission for the next one.
  - Every "commit", "push" or "tag" step written in these stage files
    means "propose it and wait for the user's command" — never do it
    automatically.
  - Read-only git commands (status, diff, log, show) are always allowed.

Branch
  Only one branch: main. No feature/stage branches, no Pull Requests.
  All work is committed directly to main and pushed to origin/main.
  From Stage 3 on, every push to main redeploys the live site, so every
  pushed commit must leave the site working (half-finished work stays
  local until it works, or is hidden from the UI).

Commits
  - Small, focused commits — one logical change each (e.g. "add cart
    reducer", not "stage 2 work"). Propose a commit whenever something
    works; the user decides when it is made (see RULE above).
  - Conventional Commits style messages, English, imperative:
      feat: add product catalog grid
      fix: keep cart quantity at minimum 1
      style: dark theme tokens for checkout form
      refactor: / docs: / chore: / test:
  - Before each commit: `npm run lint` and `npm run build` pass
    (optional later: a pre-commit hook; not required now).
  - Never commit: node_modules, dist, .env, large original images.

Pushing
  - `git push origin main` at least at the end of every working session
    (backup + visible progress), and always at the end of a stage.
  - Before pushing, review what goes out: `git log origin/main..main`
    and `git diff origin/main`.
