STAGE 4 — ANALYTICS: dataLayer, data-gtm ATTRIBUTES, GTM INSTALLATION
======================================================================

Prerequisite
------------
Stage 3 milestone reached: the store is live on GitHub Pages, all
functional checks pass, tag v1.0-no-analytics exists.
Git (workflow from Stage 1 §4): NO commit / push / tag by the AI without
the user's command. Commits go directly to main. Every push
redeploys the live site, so push only commits where the store still works
(analytics pushes without GTM are harmless to users, but a broken build or
crashing component is not). Suggested commits: "feat: typed dataLayer utility",
"feat: GTM injection plugin", "feat: track cart events", "feat: purchase
de-duplication", "feat: data-gtm attributes", "ci: pass VITE_GTM_ID to
build". If something breaks, compare with `git diff v1.0-no-analytics`.

Goal
----
Push every required interaction into window.dataLayer with correct, typed
GA4 ecommerce payloads; add data-gtm attributes; install GTM via the
official snippet when (and only when) a GTM ID is configured. No direct
GA4 / Meta calls anywhere. The store's behaviour must not change.


4.1 Architecture additions
--------------------------

  User action (click, form submit, route change)
        |
        v
  CartContext actions / router / pages  --->  src/analytics/track.ts
                                                      |
                                                      v
                                   window.dataLayer.push({ event, ecommerce })
                                                      |
                                                      v
                         Google Tag Manager (loaded only if GTM ID is set)
                                |                       |
                                v                       v
                         GA4 event tags          Meta Pixel tags
                     (Measurement ID in GTM)  (Pixel ID in GTM)

a) No analytics code talks to GA4 or Meta directly. The site ONLY pushes to
   window.dataLayer. All IDs (GA4 Measurement ID, Meta Pixel ID) live in GTM.
b) One interaction = one dataLayer push. GA4 and Meta tags in GTM both listen
   to the same event (e.g. "add_to_cart" -> GA4 add_to_cart + Meta AddToCart).
c) page_view strategy (chosen once, used everywhere):
   - The site pushes {event: "page_view", page_path, page_title,
     page_location} on initial load AND on every route change, from the
     router only.
   - In GTM the Google tag is configured with send_page_view = false, and
     GA4 Enhanced Measurement "page changes based on browser history events"
     is turned OFF. A GA4 event tag "page_view" + Meta "PageView" fire on the
     custom event "page_view". Result: exactly one page_view per view.
   - page_path is the real browser path (location.pathname), INCLUDING the
     GitHub Pages base path, so it matches what GA4 / Tag Assistant see;
     document this in Stage 5.
d) StrictMode runs effects twice in dev: events are pushed from event
   handlers or the router where possible; any effect-based event
   (view_item, view_cart, begin_checkout, purchase) is protected by a ref /
   localStorage guard so it fires once.
e) Privacy: dataLayer payloads never contain name, email, phone or delivery
   address. Only product data, totals, transaction_id and the delivery
   METHOD id.


4.2 GTM installation (configurable, safe when missing)
------------------------------------------------------
.env.example (committed)
  # Paste your container ID from tagmanager.google.com, e.g. GTM-AB12CDE
  VITE_GTM_ID=GTM-XXXXXXX
.env (local, git-ignored) — learner's real ID.

vite.config.ts — inline plugin `gtmPlugin()` using transformIndexHtml:
  - reads VITE_GTM_ID via loadEnv(mode, process.cwd())
  - if valid (/^GTM-[A-Z0-9]+$/ and !== "GTM-XXXXXXX"):
      inject official GTM <script> as high in <head> as possible
      inject official <noscript><iframe ...></noscript> right after <body>
  - else: inject nothing, print a one-line console warning during build.

GitHub Pages: the ID is NOT committed. Store it as a repository variable
(Settings -> Secrets and variables -> Actions -> Variables -> VITE_GTM_ID;
a GTM ID is public anyway, so a variable is fine) and add ONE line to the
build step of .github/workflows/deploy.yml:
    env: VITE_GTM_ID: ${{ vars.VITE_GTM_ID }}
Missing variable -> build still succeeds, site works without GTM.
After changing the ID: restart dev server (local) / re-run the workflow
(live).

src/analytics/dataLayer.ts also does `window.dataLayer = window.dataLayer || []`
so pushes never fail if GTM is absent or blocked by an ad blocker.

4.5 Event wiring (where each push happens)
------------------------------------------
Event              Fired from                         Payload notes
-----------------  ---------------------------------  ---------------------------
page_view          router: initial load + every       page_path, page_location,
                   navigate()/popstate (only place)   page_title (title updated
                                                      BEFORE push)
view_item_list     ProductGrid, IntersectionObserver  item_list_id "catalog",
                   when #catalog is ≥50% visible,     item_list_name
                   once per page view (ref guard)     "Каталог", all 4 items
                                                      with index

                   click (before navigating)

                   (guarded by ref keyed on id)       value = price
add_to_cart        CartContext.addToCart() and        item with ADDED qty,
                   increment (+)                      value = price * added qty
remove_from_cart   CartContext.removeFromCart() and   item with REMOVED qty,
                   decrement (−)                      value accordingly

                   (empty cart -> skip)
begin_checkout     CheckoutPage on open with          all lines, cart total
                   non-empty cart (guarded)

                   distinct method per checkout)      shipping_tier = method id
purchase           ConfirmationPage — see 4.6         transaction_id, value,
                                                      currency, items
click_cta          Hero CTA click                     cta_text, cta_location
form_start         first focus/input in checkout      form_name
                   form (once per checkout visit)     "checkout"
form_submit        after validation passes, before    form_name "checkout"
                   navigating to confirmation         (NO field values)


4.6 Purchase de-duplication
---------------------------
1. On valid submit the Order is saved as "glowcare_last_order" (already
   done in Stage 2).
2. ConfirmationPage effect:
     const tracked = read("glowcare_tracked_transactions")  // string[]
     if (!tracked.includes(order.transactionId)) {
       write(tracked + id)        // mark FIRST (StrictMode / fast refresh)
       trackPurchase(order)
     }
3. Refreshing /confirmation, going back/forward, or StrictMode double
   effects -> already tracked -> no second push.
4. Opening /checkout or submitting an invalid form never reaches this code.
Keep the tracked list trimmed (e.g. last 20 ids).

  data-gtm="delivery-method"     each delivery radio
  data-gtm="place-order"         "Підтвердити замовлення"

                                 a GTM click-trigger exercise only
  Product-related buttons also carry data-item-id="cream_001" etc.


4.8 Privacy rules (enforced in code review)
-------------------------------------------
- track.ts functions accept products/orders only — there is no parameter
  through which name, email or phone could be passed.
- Order stored in localStorage contains no personal fields.
- delivery method is sent as an id ("nova_poshta"), not an address.
